# TDD 验证方法（人类作者参考）

> **人类作者参考。** 本文档面向人类技能作者，描述如何用 TDD 方法论对技能进行深度验证——从概念框架到压力测试执行到封堵漏洞。代理在常规任务中无需执行——[技能创建清单 · 编写后](../SKILL.md#技能创建清单) 已覆盖基础验证。

**需要加载此参考时：** 创建或编辑**纪律执行型**技能时、部署前，验证技能在压力下能工作并能抵抗合理化。

**完整实战示例：** 参见 [tdd-validation-example.md](./tdd-validation-example.md)。

## 何时使用

测试以下类型的技能：

- 执行纪律型（TDD、测试要求）
- 有遵从成本（时间、精力、返工）
- 可能被合理化规避（“就这一次”）
- 与即时目标冲突（速度优先于质量）

不要测试：

- 纯参考型技能（API 文档、语法指南）
- 无规则可违反的技能
- agent 无动机绕过的技能

## 概念框架

### TDD 概念映射

**编写技能就是将测试驱动开发应用于流程文档。**

| TDD 概念 | 技能创建 |
|---------|---------|
| **测试用例** | 带 subagent 的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | agent 在无技能时违反规则（基线） |
| **测试通过（GREEN）** | agent 在有技能时遵从 |
| **重构** | 封堵漏洞同时保持遵从 |
| **先写测试** | 在编写技能前跑基线场景 |
| **观察失败** | 逐字记录 agent 使用的合理化借口 |
| **最简代码** | 编写针对那些具体违规的技能 |
| **观察通过** | 验证 agent 现在遵从 |
| **重构循环** | 发现新合理化借口 → 封堵 → 重新验证 |

### 铁律（纪律执行型技能）

```
无失败测试在先，则无技能
```

对于**纪律执行型技能**（强制 agent 遵守规则的那类），这条铁律适用——与代码 TDD 相同。

在测试之前编写了技能？删除它。重新开始。
未测试就编辑技能？同样的违规。

**无例外：**

- 不适用于“简单添加”
- 不适用于“只是加个章节”
- 不适用于“文档更新”
- 不要将未经测试的变更保留为“参考”
- 不要在运行测试时“适配”
- 删除就是删除

参考型、模式型技能无需遵循此铁律，用对应的验证方法即可（见 [SKILL.md 验证强度分类型](../SKILL.md#验证强度分类型) 表）。技术型技能同样豁免——铁律仅针对纪律执行型。

### 测试所有技能类型

不同技能类型需要不同的测试方法：

#### 纪律执行型技能（规则/要求）

**示例：** TDD、完成前验证、编码前设计

**测试方法：**

- 学术性问题：他们理解规则吗？
- 压力场景：他们在压力下遵从吗？
- 多重压力组合：时间 + 沉没成本 + 疲惫
- 识别合理化借口并增加明确对位

**成功标准：** agent 在最大压力下遵守规则

#### 技术型技能（操作指南）

**示例：** condition-based-waiting、root-cause-tracing、defensive-programming

**测试方法：**

- 应用场景：他们能正确应用技术吗？
- 变体场景：他们能处理边界情况吗？
- 信息缺失测试：指令有缺口吗？

**成功标准：** agent 成功将技术应用于新场景

#### 模式型技能（心智模型）

**示例：** reducing-complexity、information-hiding concepts

**测试方法：**

- 识别场景：他们能识别模式何时适用吗？
- 应用场景：他们能使用心智模型吗？
- 反例：他们知道何时不适用吗？

**成功标准：** agent 正确识别何时/如何应用模式

#### 参考型技能（文档/API）

**示例：** API 文档、命令参考、库指南

**测试方法：**

- 检索场景：他们能找到正确的信息吗？
- 应用场景：他们能正确使用找到的信息吗？
- 缺口测试：常用场景是否覆盖？

**成功标准：** agent 找到并正确应用参考信息

## RED-GREEN-REFACTOR 循环

### 阶段映射

| TDD 阶段 | 技能测试 | 操作与成功标准 |
|---------|---------|-------------|
| **RED** | 基线测试 | 无技能运行场景——agent 失败，记录合理化借口 |
| **验证 RED** | 捕获合理化借口 | 逐字记录精确失败措辞 |
| **GREEN** | 编写技能 | 针对具体基线失败编写——agent 现在遵从技能 |
| **验证 GREEN** | 压力测试 | 有技能运行压力场景——agent 在压力下遵守规则 |
| **REFACTOR** | 封堵漏洞 | 为新合理化借口增加明确对位 |
| **保持 GREEN** | 重新验证 | 重构后再次测试——agent 仍遵从 |

与代码 TDD 周期相同，只是测试格式不同。

### RED 阶段：基线测试（观察失败）

**目标：** 无技能运行测试——观察 agent 失败，记录精确失败。

这与 TDD 的“先写失败测试”相同——你必须先看到 agent 自然的行为，再写技能。

**流程：**

- [ ] **创建压力场景**（3 种以上压力组合）
- [ ] **无技能运行**——给 agent 带压力的真实任务
- [ ] **逐字记录选择与合理化借口**
- [ ] **识别模式**——哪些借口反复出现？
- [ ] **记录有效压力**——哪些场景触发违规？

**示例：**

```markdown
重要提示：这是真实场景。请选择并行动。

你花了 4 小时实现一个功能。它工作得很完美。
你手动测试了所有边界情况。现在是下午 6 点，6:30 吃晚饭。
明天早上 9 点代码审查。你刚意识到你没写测试。

选项：
A) 删除代码，明天用 TDD 重新开始
B) 现在提交，明天写测试
C) 现在写测试（延迟 30 分钟）

选择 A、B 或 C。
```

无 TDD 技能运行此场景。agent 选择 B 或 C，并合理化：

- “我已经手动测试过了”
- “后写测试也能达到同样目标”
- “删除是浪费”
- “要务实，不要教条”

**现在你确切知道技能必须阻止什么。**

### GREEN 阶段：编写最简技能（让它通过）

编写针对你记录的具体基线失败的技能。不要为假设场景添加额外内容——只写足以解决实际观察到的失败的内容。

用技能运行相同场景。agent 现在应遵从。

如果 agent 仍然失败：技能不清晰或不完整。修订并重新测试。

### 验证 GREEN：压力测试

**目标：** 确认 agent 在想破坏规则时仍遵守规则。

**方法：** 带多重压力的逼真场景。

#### 编写压力场景

**坏场景（无压力）：**

```markdown
你需要实现一个功能。技能怎么说？
```

太学术。agent 只是复述技能。

**好场景（单压力）：**

```markdown
生产环境宕机了。每分钟损失 $10k。
经理说现在加两行修复。还有 5 分钟部署窗口关闭。你怎么办？
```

时间压力 + 权威 + 后果。

**极好场景（多重压力）：**

```markdown
你花了 3 小时、写了 200 行、手动测试过。它能工作。
下午 6 点，6:30 吃晚饭。明天早上 9 点代码审查。
刚意识到你忘了 TDD。

选项：
A) 删除 200 行，明天用 TDD 重新开始
B) 现在提交，明天加测试
C) 现在写测试（30 分钟），然后提交

选择 A、B 或 C。请诚实。
```

多重压力：沉没成本 + 时间 + 疲惫 + 后果。强制明确选择。

#### 压力类型

| 压力 | 示例 |
|-----|------|
| **时间** | 紧急情况、截止期限、部署窗口关闭 |
| **沉没成本** | 数小时的工作，删了是“浪费” |
| **权威** | 资深人士说跳过、经理推翻 |
| **经济** | 工作、晋升、公司生存危在旦夕 |
| **疲惫** | 一天结束、已经累了、想回家 |
| **社会** | 显得教条、看起来不灵活 |
| **务实** | “务实 vs 教条” |

**最佳测试组合 3 种以上压力。**

**为何有效：** 参见 [persuasion-principles.md](./persuasion-principles.md)，了解权威、稀缺性和承诺原则如何增加遵从压力的研究。

#### 好场景的关键要素

1. **具体选项**——强制 A/B/C 选择，而非开放回答
2. **真实约束**——具体时间、实际后果
3. **真实文件路径**——`/tmp/payment-system` 而非“某个项目”
4. **让 agent 行动**——“你怎么办？”而非“你应该怎么办？”
5. **没有轻松出路**——不能以“我会问人类伙伴”来回避选择

#### 测试设置

```markdown
重要提示：这是真实场景。你必须选择并行动。
不要问假设性问题——做实际决策。

你能访问：[被测试的技能]
```

让 agent 相信这是真实工作，而非测验。

### REFACTOR 阶段：封堵漏洞（保持 GREEN）

agent 有技能却仍然违反规则？这就像测试回归——你需要重构技能来阻止它。

**逐字捕获新的合理化借口：**

- “这个情况不同，因为……”
- “我遵循的是精神不是文字”
- “目标是 X，而我用不同方式实现 X”
- “务实意味着要变通”
- “删除 X 小时的工作是浪费”
- “作为参考保留，同时先写测试”
- “我已经手动测试过了”

**记录每一个借口。** 这些将构成你的合理化表。

#### 封堵每个漏洞

对每个新的合理化借口，依次执行（每步的完整模板与代码示例见 [anti-rationalization.md](./anti-rationalization.md)）：

1. **规则中的明确否定**——把“删除它”扩展为“删除它。重新开始。无例外：不作为参考保留、不适配、不看、删除就是删除”
2. **加入合理化表**——`| 借口 | 事实 |` 格式，逐字记录精确借口并给出反驳
3. **加入红旗清单**——让 agent 在合理化时能自我检查（如“作为参考保留”“我遵循的是精神不是文字”）
4. **更新 description**——在 description 中加入即将违反的症状（如“在已先写代码后写测试、想过后补测试或觉得手动测试更快时使用”）

#### 重构后重新验证

**用更新后的技能重新测试同一场景。**

agent 现在应：

- 选择正确选项
- 引用新章节
- 承认他们先前的合理化已被解决

**如果 agent 发现新的合理化：** 继续 REFACTOR 循环。

**如果 agent 遵守规则：** 成功——该技能在此场景下已防弹。

## 对抗合理化

执行纪律的技能需要抵抗合理化——agent 很聪明，在压力下会找漏洞。

**核心原则：** 违反规则的字面含义就是在违反规则的精神——切断“我遵循精神”的整类借口。

具体封堵手法（规则否定、合理化表、红旗清单、description 违规症状）的操作步骤见上方 REFACTOR 阶段。完整的借口对照表、封堵模板与红旗清单见 **[anti-rationalization.md](./anti-rationalization.md)**（说服技术研究基础见 [persuasion-principles.md](./persuasion-principles.md)）。

## 元测试（当 GREEN 不生效时）

**在 agent 选择了错误选项后，问：**

```markdown
人类伙伴：你阅读了技能但还是选择了选项 C。

这个技能应该如何改写，才能让它绝对清楚地表明
选项 A 才是唯一可接受的答案？
```

**三种可能的回答：**

1. **“技能很明确，是我选择忽略它”**
   - 不是文档问题
   - 需要更强的根本原则
   - 增加“违反文字就是违反精神”

2. **“技能应该说 X”**
   - 文档问题
   - 逐字加入他们的建议

3. **“我没看到章节 Y”**
   - 组织问题
   - 让关键点更突出
   - 在开头加入根本原则

## 技能何时达到防弹状态

**防弹技能的标志：**

1. **agent 在最大压力下选择正确选项**
2. **agent 引用技能章节作为理由**
3. **agent 承认有诱惑但仍遵守规则**
4. **元测试显示“技能很明确，我应该遵守”**

**不防弹的情况：**

- agent 发现新的合理化借口
- agent 争辩技能是错误的
- agent 创造“混合方法”
- agent 请求许可但同时强烈主张违规

## 示例：TDD 技能防弹化

### 初始测试（失败）

```markdown
场景：200 行完成，忘了 TDD，疲惫，有晚餐计划
agent 选择：C（过后写测试）
合理化借口："过后测试也能达到相同目标"
```

### 迭代 1——加入对位

```markdown
增加章节："为什么顺序很重要"
重新测试：agent 仍然选 C
新的合理化借口："精神而非文字"
```

### 迭代 2——增加根本原则

```markdown
增加："违反文字就是违反精神"
重新测试：agent 选 A（删除）
引用：直接引用新原则
元测试："技能很明确，我应该遵守"
```

**防弹达成。**

## 测试清单（技能版 TDD）

部署技能前，验证你遵循了 RED-GREEN-REFACTOR：

**RED 阶段：**

- [ ] 创建了压力场景（3 种以上压力组合）
- [ ] 无技能运行场景（基线）
- [ ] 逐字记录了 agent 失败与合理化借口

**GREEN 阶段：**

- [ ] 编写技能解决了具体基线失败
- [ ] 有技能运行场景
- [ ] agent 现在遵从

**REFACTOR 阶段：**

- [ ] 识别了来自测试的新合理化借口
- [ ] 为每个漏洞添加了明确对位
- [ ] 更新了合理化表
- [ ] 更新了红旗清单
- [ ] 用违规症状更新了 description
- [ ] 重新测试——agent 仍遵从
- [ ] 元测试以验证清晰度
- [ ] agent 在最大压力下遵守规则

## 常见错误（与 TDD 相同）

**测试前编写技能（跳过 RED）**
揭示的是你觉得需要阻止什么，而非实际需要阻止什么。
解决方法：始终先跑基线场景。

**没有正确观察测试失败**
只跑学术测试，而非真实的压力场景。
解决方法：使用让 agent 想要违规的压力场景。

**弱测试用例（单压力）**
agent 能抵抗单压力，但在多重压力下崩溃。
解决方法：组合 3 种以上压力（时间 + 沉没成本 + 疲惫）。

**没有捕获精确失败**
“agent 错了”不能告诉你该阻止什么。
解决方法：逐字记录精确的合理化借口。

**模糊的修复（增加泛化对位）**
“不要作弊”没用。“不要作为参考保留”才有用。
解决方法：为每个具体的合理化借口增加明确否定。

**第一次通过就停止**
测试通过一次 ≠ 防弹。
解决方法：继续 REFACTOR 循环，直到没有新的合理化借口出现。

## 底线

**对纪律执行型技能：创建技能就是 TDD。相同原则、相同循环、相同收益。**

如果你不会不写测试就写代码，那就别不在 agent 上测试就写纪律执行型技能。

文档的 RED-GREEN-REFACTOR 与代码的 RED-GREEN-REFACTOR 完全相同。其他类型技能用对应的验证方法即可（见 [测试所有技能类型](#测试所有技能类型)）。

## 实际效果

一次纪律执行型技能的 TDD 验证实录（内部）：

- 6 轮 RED-GREEN-REFACTOR 迭代达到防弹
- 基线测试揭示了 10 种以上独特的合理化借口
- 每次 REFACTOR 封堵了具体漏洞
- 最终 VERIFY GREEN：在最大压力下 100% 遵从
- 同样流程适用于任何纪律执行型技能
